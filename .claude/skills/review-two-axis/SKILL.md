# Review Two-Axis：雙軸審查

對使用者指定的審查對象做雙軸審查：

- **Spec 軸**：產出是否忠實完成題目或 spec 的要求？有沒有漏做、做一半、做了範圍外的事？
- **Standards 軸**：程式碼（或查詢、文件）的品質與正確性是否過關？

兩軸各自用**平行的 fresh-context subagent** 執行，互不污染 context，最後由本 skill 並排彙整。

本 skill 是六步驟流程的**步驟 3 驗證**。依 `CLAUDE.md`：寫的人不驗收自己的產出，所以審查一律交給沒看過實作過程的 subagent。

## 流程

### 1. 確定審查對象

審查對象由**使用者指定**，可以是：
- 檔案或目錄清單（例如 `LionDEExam/submission/part_a/`）；
- 一段 diff（使用者貼上，或使用者指定的 `git diff` 指令，例如 `git diff -- <路徑>` 看未 commit 的改動）。

使用者沒指定就問，不要自己猜範圍。開始前先確認對象存在且非空（`ls` 檔案、或執行 diff 指令確認有輸出）；路徑錯誤或 diff 為空要在這一步失敗，不要等到兩個 subagent 裡才發現。repo 沒有任何 commit 時，直接以檔案清單為審查對象。

### 2. 找 spec 來源

依序找：
1. 使用者作為參數給的路徑。
2. 題目全文 `LionDEExam/01_考題卷_資料工程師TakeHome.md` 中對應 Part 的段落。
3. 專案 `.claude/` 下與此任務相關的 spec、plan 文件，或 process-log 該任務步驟 1 的拆解結果。
4. 都找不到就問使用者。使用者說沒有 spec 時，略過 Spec subagent，並在報告中寫明「無 spec，未做 Spec 軸」。

### 3. 找 standards 來源

蒐集專案中規範產出寫法的文件，至少包含 `CLAUDE.md`（例如：資料品質結論必須附實際查詢與輸出、繳交物一律 Markdown、Part C 每節要有歸屬標註）。

除了專案文件，Standards 軸一律帶上下列**基準檢查**。兩條規則約束它：
- **專案規範優先**：專案文件明確允許的做法，基準不得再標為問題。
- **一律是判斷題**：基準項目是有標籤的推測（例如「可能是 Duplicated Code」），不是硬性違規。工具已經會強制的（formatter、linter）略過。

**正確性基準**（資料工程產出常見錯誤）：
- **結論無證據**：資料品質或數字結論沒有附實際執行的查詢與輸出。→ 補上查詢與輸出，或刪除該結論。
- **筆數對不上**：前後步驟的 row count、去重前後數量、join 前後數量無法對帳。→ 加 checksum 或 count 對帳。
- **Join／去重邏輯錯誤**：join key 不唯一造成筆數膨脹、去重鍵選錯、NULL 被當成相同值或被默默丟掉。→ 用查詢驗證 key 的唯一性與 NULL 分佈。
- **時間與型別陷阱**：時區、日期格式、字串與數字混用、浮點金額。→ 明確轉型並在文件寫出假設。
- **默默丟資料**：filter 或錯誤處理吞掉異常列而沒有記錄筆數。→ 記錄被排除的筆數與原因。

**程式碼味道基準**（Fowler《Refactoring》第 3 章的精選子集）。格式為「是什麼 → 怎麼修」，拿來比對審查對象：
- **Mysterious Name**：名稱看不出它做什麼或裝什麼。→ 改名；想不出誠實的名字，代表設計本身不清楚。
- **Duplicated Code**：同樣的邏輯在多處出現。→ 抽出共用部分，兩處都呼叫它。
- **Feature Envy**：函式取用別的物件的資料多於自己的。→ 把函式移到它羨慕的資料那邊。
- **Data Clumps**：同一組欄位或參數總是一起出現。→ 包成一個型別傳遞。
- **Primitive Obsession**：用原始型別或字串代表值得有自己型別的領域概念。→ 給它一個小型別。
- **Repeated Switches**：同樣的 `switch`／`if` 串在多處重複判斷同一個型別。→ 改用多型，或共用一張 map。
- **Shotgun Surgery**：一個邏輯改動需要散落各檔的修改。→ 把會一起變的東西集中到一個模組。
- **Divergent Change**：同一個檔案因多個不相關的理由被修改。→ 拆開，讓每個模組只為一個理由改變。
- **Speculative Generality**：為 spec 沒要求的需求加抽象、參數或 hook。→ 刪掉，等真的需要再加。
- **Message Chains**：呼叫端依賴長串 `a.b().c().d()` 導航。→ 用第一個物件上的一個方法包起來。
- **Middle Man**：類別或函式大多只是轉手呼叫。→ 拿掉，直接呼叫真正的目標。
- **Refused Bequest**：子類別忽略或覆寫大部分繼承來的東西。→ 放棄繼承，改用組合。

### 4. 平行派出兩個 subagent

兩個 subagent 呼叫**在同一則訊息一起發出**，在前景執行，收齊報告後彙整。prompt 只給目的和素材，**不給實作過程**（「實作過程你不知道也不需要知道，請獨立判斷」這句要保留），避免驗收者被實作者的說法帶著走。

**Standards subagent 的 prompt** 要包含：
- 審查對象（檔案清單或 diff 指令／內容）。
- 步驟 3 找到的規範文件路徑，**加上上面兩組基準全文**（subagent 看不到本 skill）。
- 指示：「能執行的就自己執行（跑腳本、跑查詢、對筆數），不要相信註解或文件的自述。依檔案或段落回報：(a) 違反專案規範之處，引用規範（檔案＋規則）；(b) 觸發的基準項目，寫出名稱並引用片段，附 `檔案:行號`。區分硬性違規與判斷題：違反專案文件可以是硬性的，基準項目一律是判斷題。工具已強制的略過。只報中等信心以上的問題。400 字以內，繁體中文。」

**Spec subagent 的 prompt** 要包含：
- 審查對象。
- spec 的路徑或內容。
- 指示：「回報：(a) spec 要求但缺漏或只做一半的項目；(b) 產出中 spec 沒要求的行為（範圍外）；(c) 看似完成但做法有誤的項目。每條引用對應的 spec 原文，附 `檔案:行號`。只報中等信心以上的問題。400 字以內，繁體中文。」

沒有 spec 就略過 Spec subagent，並在最終報告註明。

### 5. 彙整

在 `## Spec` 與 `## Standards` 兩個標題下呈現兩份報告，原文或稍加整理。**不要合併或重新排序**兩軸的發現，因為兩軸刻意分開（見「為什麼分兩軸」）。

最後一行摘要：每軸的發現數量，以及**各軸內**最嚴重的問題（若有）。不要跨軸選出單一最嚴重問題，那正是分軸要避免的重排。

### 6. 交給使用者記錄

審查結果是 process-log 的素材，依 `CLAUDE.md` 紀錄規則據實記錄：
- **步驟 3 驗證**：寫審查方法（雙軸審查、審查對象、spec 來源）與結果摘要。
- **步驟 4 修正**：每個被採納的問題寫成一條 `<P>-NN.k`，**發現者寫「驗收 agent」**，不要寫成 AI 自查或使用者；附 subagent 引用的 `檔案:行號` 作為證據。
- 哪些問題要修、哪些不採納，由使用者決定。AI 列出選項與代價，不自行定案。
- 修完後要重新派 fresh-context subagent 驗收，不由修的人自己驗收。

寫入 process-log 後，回覆最後一行寫「已記錄 <P>-NN 步驟 N」。

## 為什麼分兩軸

一份產出可能通過一軸、卻沒通過另一軸：

- 程式碼品質無可挑剔，但做的不是題目要的 → **Standards 過，Spec 不過**。
- 完全照題目要求做，但查詢邏輯有錯或違反專案規範 → **Spec 過，Standards 不過**。

分開報告，才不會讓一軸的結果掩蓋另一軸。
