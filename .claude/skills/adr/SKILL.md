# ADR：記錄決策與其理由

ADR 的價值在於記下**做了什麼決定**以及**為什麼**，讓面談或日後的讀者看得懂「為什麼這樣做」。本專案前提（見 `CLAUDE.md`）：AI 不替使用者定案，所以 AI 準備素材，使用者寫結論。

## 門檻：三條件都成立才寫

1. **難回頭**：之後改變主意的成本可觀。
2. **沒脈絡會覺得奇怪**：讀者看到產出會問「為什麼要這樣做？」
3. **有真的替代方案**：確實存在其他合理選項，而且因為特定理由選了其中一個。

缺任何一條就不寫 ADR，改為在 `LionDEExam/submission/ai-collab/process-log.md` 記一個使用者定案的事件即可（格式照 `ai-collab/README.md`）。容易回頭的，改就好；不奇怪的，沒人會問；沒有替代方案的，沒有東西可記。

**典型符合的決策**（以資料工程題為例）：
- **資料模型或 pipeline 的形狀**：例如分層設計、增量或全量處理。
- **有鎖定效應的技術選型**：儲存格式、排程工具、資料庫。不是每個 library 都算。
- **邊界與範圍**：哪些資料問題處理、哪些刻意不處理。明確說「不做」和說「要做」一樣有價值。
- **刻意偏離直覺做法**：例如不刪異常資料而是標記。理性讀者會以為反過來的，都值得記，避免別人「修好」刻意的設計。
- **程式碼看不到的限制**：題目規定、資料來源限制、效能要求。
- **不明顯的被否決方案**：否決理由不直觀時要記，否則會有人再提一次。

AI 判斷某決策符合門檻時，**主動提議**寫 ADR，但不擅自建立；使用者同意後才寫。

## 位置與編號

- 路徑：`LionDEExam/submission/decisions/ADR-NN-<主題>.md`。目錄不存在時，寫第一份 ADR 時才建立。
- 編號**跨 Part 共用**、兩位數：掃描 `LionDEExam/submission/decisions/` 中現有最大號，+1。沒有任何 ADR 時從 `ADR-01` 開始。
- `<主題>` 用簡短 kebab-case 或中文短詞，與標題一致。

## 範本（照用）

```md
# ADR-NN｜<決策標題>
- 狀態：草稿／已定案／被 ADR-NN 取代
- Part：
- 關聯：<process-log.md 事件標題>
## 背景
## 選項
| 選項 | 好處 | 代價 |
|---|---|---|
## 決定〔使用者撰寫〕
## 理由〔使用者撰寫〕
## 後果
```

## 誰寫哪一節

| 節 | 誰寫 | 要求 |
|---|---|---|
| 狀態 | AI 建立時填「草稿」 | **只有使用者能改成「已定案」**，AI 不得修改 |
| Part、關聯 | AI | 關聯填 `process-log.md` 中對應事件的標題 |
| 背景 | AI | 問題是什麼、為什麼需要決定。**附資料證據**：實際執行的查詢與輸出、函式名＋可搜尋的程式碼片段（不寫行號）、筆數。不能憑欄位名或常識推論 |
| 選項 | AI | 至少兩個真的可行選項，每個列好處與代價；代價要具體（多花什麼、失去什麼、風險在哪） |
| 決定 | 使用者 | AI 留空，或給一段標 `〔待使用者確認〕` 的草稿 |
| 理由 | 使用者 | 同上。理由要用使用者自己的話，面談會追問 |
| 後果 | AI | 選了之後的下游影響：哪些產出要跟著改、留下什麼限制或技術債。若依決定而異，按選項分列 |

## 寫完之後

1. 回報 ADR 路徑，並明確列出「決定」「理由」兩節等使用者撰寫。
2. 在 `LionDEExam/submission/ai-collab/process-log.md` 記一個定案事件（格式照 `ai-collab/README.md`）：AI 記事件的標題與依據，「經過」留給使用者用自己的話寫，或只寫「見 ADR-NN」。AI 不代寫決定與理由；記錄後回覆最後一行寫「已記錄事件：<標題>」。
3. 決策若被推翻，不刪舊 ADR：新開一份 ADR，並在舊 ADR 的狀態欄由使用者註明「被 ADR-NN 取代」。
