## 0. 怎麼讀這份文件

**每條假設的分類標在小節開頭：**

- 〔使用者假設〕：使用者自己做的業務判斷，理由是他的話。選項可能由 AI 列出。
- 〔AI 提出、使用者採用〕：process-log 註明是 AI 的建議或 AI 寫的說法，使用者接受。
- 〔官方說明〕：題目或 `candidate_package/README.md` 已經寫明，**不算假設**，只在需要對照時列出。

**引用規則：** 「」裡是逐字原話，出處是 [process-log](ai-collab/process-log.md) 的事件標題或 ADR 編號。官方文字與一般的名詞、說法用“”標示，不是使用者原話。資料數字出自 [A-3 資料品質報告](part_a/data-quality-report.md)（以下簡稱 A-3）與 `notes/part_a/` 的筆記，查詢與輸出都在那些檔案裡。

**本文件不做新的決定**：所有內容都已在 process-log 或 ADR 定案；尚未定案的事標〔待使用者確認〕。

## 1. 訂單狀態

官方只給了 4 個狀態值（created／paid／completed／cancelled），沒說它們之間怎麼轉移。完整的狀態圖見 [`notes/part_a/order-state-machine.md`](notes/part_a/order-state-machine.md)。

### 1.1 訂單流程單向，取消後不能恢復

〔使用者假設〕

| 欄位 | 內容 |
|---|---|
| 假設 | 訂單狀態只會往前走；cancelled 之後不會再變成其他狀態 |
| 為什麼需要假設 | 官方只列狀態值，沒有轉移規則。官方寫了“以 `updated_at` 區分新舊”，但沒說舊狀態能不能回來 |
| 使用者原話 | 「那先簡單假設不能恢復」（process-log「假設訂單流程單向：取消後不能恢復」）；之後用它決定新舊判斷：「照 updated_at，符合狀態機單向假設」（process-log「增量新舊以 updated_at 判斷」） |
| 依據與資料證據 | **支持**：day1→day2 的 25 張單，照檔案順序是 cancelled → paid，照 `updated_at` 是 paid → cancelled；在這條假設下只有後者合理（A-3 2.5 節；`notes/part_a/schema-inference/order-time.md` 的 L4）。**限制**：demo 中同一張單狀態真的有變的只有這 25 組，其他轉移沒有資料證據 |
| 用在哪裡 | Part A：狀態機用可達性檢查，往回走的轉移（cancelled → paid 等）進隔離表；晚到的舊事件不覆寫 fact（ADR-05 背景）；ADR-04 一張訂單一列、只存最新狀態。Part B：審查去重與 MERGE 時，以 `updated_at` 取最新為正確行為。Part C：「取消率」「目前狀態」的定義以最新狀態為準 |
| 如果假設錯了 | 若業務允許取消後恢復，L4 的 25 張單應該是 paid 而不是 cancelled，取消率會算錯；往回走的事件會被誤隔離；若要保存每個里程碑的時間，fact 型態要重新考慮 |

### 1.2 completed 之後不能取消

〔使用者假設〕

| 欄位 | 內容 |
|---|---|
| 假設 | 出團完成的訂單不會再被取消（例如出團後才申請退款，不以 cancelled 表示） |
| 為什麼需要假設 | 官方沒說；資料裡的 completed → cancelled 只出現在撞號列，不能當同一張單的歷程 |
| 使用者原話 | 「先假設completed後不能取消」（process-log「假設 completed 後不能取消」） |
| 依據與資料證據 | **無直接證據**：同一張單（會員、金額、下單時間都相同）沒有 completed → cancelled 的例子（`order-state-machine.md`“每條轉移的證據”）。ADR-03 也用這條當輔證：撞號列若當成更新，會出現 completed → cancelled |
| 用在哪裡 | Part A：可達性檢查中 completed → cancelled 不合法，進隔離表；ADR-03 撞號判定的輔證。Part C：已完成營收不會因後續取消而減少 |
| 如果假設錯了 | 出團後退款被當成不合法事件隔離，取消率偏低；ADR-03 少了一條輔證（主證據是會員、金額、下單時間 0 筆相同，不受影響） |

### 1.3 completed 一定先經過 paid

〔使用者假設〕

| 欄位 | 內容 |
|---|---|
| 假設 | 沒有 created → completed 的直接跳轉（例如現場付款的票券）；completed 之前一定付過款 |
| 為什麼需要假設 | 官方沒說；資料沒有任何一張單看得到完整歷程 |
| 使用者原話 | 「我先假設不行」（process-log「狀態機定案：created 不能直接跳到 completed」）。後來因為無法確定上游送的是事件還是快照，檢查改成可達性：「在沒辦法確定是事件驅動還是快照的情況下 逐段也用可達性」（process-log「狀態檢查一律用可達性，不用一步轉移表」） |
| 依據與資料證據 | **無直接證據**。本資料沒有出現 created → completed（A-3 附錄 B 的 Q-SM.chain，防護性設計） |
| 用在哪裡 | Part A：看到 created → completed 視為「中間的 paid 沒拍到」，合法但計數，不隔離。所以這條假設**目前只影響說明，不影響管線結果** |
| 如果假設錯了 | 管線結果不變（可達性本來就放行）；只有「跳過中間狀態」的計數意義改變：它可能是正常流程，不是漏送 |

### 1.4 completed 代表出團完成

〔使用者假設〕**與資料衝突**

| 欄位 | 內容 |
|---|---|
| 假設 | completed 是「已出團」，不是「交易完成」 |
| 為什麼需要假設 | 官方只寫狀態值 `completed`，沒有定義 |
| 使用者原話 | 「completed先假設成出團完成」（process-log「假設 completed 是出團完成，與 base 資料衝突」）；看到衝突數字後維持假設：「先把狀態規則定下來 之後比較好處理」（process-log「completed 維持出團完成，28,612 列當資料品質問題」） |
| 依據與資料證據 | **衝突**：base 計入 fact 的 completed 共 28,578 張，全部在最後一次更新時出發日還沒到，相差 4～119 天（A-3 2.3 節；去重前 base 為 28,612 列，見 `order-state-machine.md`）。已排除時區：`updated_at` 全是 `+08:00`，時區最多差 1 天。**反向證據**：以 07-01 為基準，出發日已過卻仍是 paid 的 9,234 張、仍是 created 的 3,053 張，狀態和出發日在資料裡沒有關聯（A-3 2.3 節） |
| 用在哪裡 | Part A：狀態機的轉移規則（1.2、1.3 都建立在“completed 是最後一步”上）；這 28,578 張照原樣寫入，只在 A-3 記錄。Part C：易混名詞表寫“已完成不等於已出團”，問出團改用出發日是否已過（`part_c/README.md` 的 `has_departed`）。模組 E：`questions.json` 的 Q15「狀態為 completed 的比例」照字面算，不解讀成出團率 |
| 如果假設錯了 | 若 completed 其實是交易完成，資料就合理，A-3 2.3 節不算品質問題；1.2 的「completed 後不能取消」也要重想（交易完成後仍可能取消） |

## 2. 訂單身分

### 2.1 訂單的基本資訊不能被修改

〔使用者假設〕**與官方說明不同**

| 欄位 | 內容 |
|---|---|
| 假設 | 同一張訂單的會員、下單時間、金額不會變；只有狀態會變。增量檔裡同 `order_id` 但這三欄任一不同的列，是另一張單撞了號 |
| 為什麼需要假設 | 官方寫增量檔“含新訂單與舊訂單的狀態更新事件”，但沒說哪些欄位可以改；資料裡同編號的列內容完全不同 |
| 使用者原話 | 「把撞號當 noise 處理」，理由原本是「先假設訂單狀態不能被改寫」（process-log「增量檔與 base 撞號的列當 noise 處理」）；ADR 定稿時改寫為「訂單的基本資訊不能被修改」（ADR-03；process-log「ADR-01～04 定稿」）。原意是內容不能改、狀態可以變 |
| 依據與資料證據 | **支持**：三天共 1,808 列和 base 同編號，會員、金額、下單時間相同的都是 0 列；幣別、通路、狀態相同的列數落在隨機配對的期望值附近（ADR-03 背景；A-3 2.2 節）。**限制**：只能證明兩邊統計上無關，排除不了「上游允許整張單被改寫」這種業務規則（ADR-03）。**和官方衝突**：照這條假設，三天的增量檔沒有任何一筆舊訂單狀態更新生效 |
| 用在哪裡 | Part A：撞號列進隔離表，不覆寫 fact；增量同檔的 6 組撞號同樣處理。Part B：審查 MERGE 時，只用 `order_id` 比對會把撞號當更新。Part C：營收、取消率、會員歸屬都以 base 的內容為準；給上游的建議是確認編號怎麼產生 |
| 如果假設錯了 | 若真的是舊訂單的合法更新，1,776 張舊訂單的狀態變化被漏掉；照官方說法處理則取消率從 12.73% 變 13.31%（A-3 2.2 節）。隔離表保留原始列，規則改了可以重新處理 |

### 2.2 只差幾秒的相同列是網路重送

〔使用者假設〕（去重規則由 AI 提出）

| 欄位 | 內容 |
|---|---|
| 假設 | 除了 `updated_at` 外全部相同、而且時間上相鄰的列，是寫入端因網路波動重送，不是兩次真的狀態事件 |
| 為什麼需要假設 | 官方只說增量檔同一 `order_id` 可能出現多次；base 是全量，卻也有同編號兩列 |
| 使用者原話 | 「v7根據我的經驗是網路波動導致的重複寫入 可以重寫入端或是schena的unique index改善」（process-log「V7 base 重複列：使用者判斷是網路波動造成的重複寫入」）；「網路重送造成的重複，留最新一列就好」（process-log「完全相同的重複列：取 updated_at 最新一列」）；「中間如果有出現其他狀態 不能當作延遲」（process-log「重複只算時間上相鄰的相同列」） |
| 依據與資料證據 | **支持**：base 40 組重複只差 `updated_at` 2～29 秒；增量同檔 45 組連狀態都相同，只差 `updated_at`（`notes/part_a/schema-inference/order-identity.md` 的 V7、J1；A-3 3.3 節） |
| 用在哪裡 | Part A：留 `updated_at` 最新一列，其餘標 `duplicate`。Part C：給上游的建議（寫入端冪等鍵）；Kafka 討論時說明重送要靠上游唯一鍵（process-log「Kafka 不放進 Part A，移到 Part C」） |
| 如果假設錯了 | 若同狀態重送其實代表兩次業務事件（例如兩次付款），留一列會漏算；本資料這些列狀態相同，對營收與取消率沒有影響 |

## 3. 金額與幣別

### 3.1 amount 是折扣前金額

〔使用者假設〕

| 欄位 | 內容 |
|---|---|
| 假設 | `amount` 是折扣前的原幣別金額；折扣後金額＝台幣金額 − coupon |
| 為什麼需要假設 | 官方只寫 `amount`（原幣別金額），沒說折扣前或後 |
| 使用者原話 | 「可以定義好業務邏輯處理」（process-log「A-3：哪些品質問題要處理、哪些只記錄」）；「那折扣前」，理由「我的設計傾向紀錄所有金額」（process-log「J10：amount 定義為折扣前，fact 加 net_amount_twd」） |
| 依據與資料證據 | **資料分辨不出來**：coupon 最多 950 台幣，訂單金額中位數約 20 萬台幣，差距不到 0.5%，比值檢查鑑別力很弱（`notes/part_a/schema-inference/order-amount.md` 的 J10）。**官方對照**：模組 E 的 `questions.json` 把淨營收定義為 “SUM(amount_twd - coupon_discount_twd)”，和折扣前的解讀一致（那是模組 E 的迷你資料倉，不是這份 dataset 的說明） |
| 用在哪裡 | Part A：fact 存 `amount_twd`（折扣前）與 `net_amount_twd`。Part C：指標實體表的折扣前後兩欄。**「營收」指標預設用折扣前還是折扣後〔待使用者確認〕**：J10 只定了欄位，沒定指標預設（`part_c/README.md`） |
| 如果假設錯了 | 若 `amount` 是折扣後，`net_amount_twd` 等於多扣一次折扣；營收總數影響很小（不到 0.5%），但“淨營收”語意錯 |

### 3.2 NTD 就是 TWD

〔AI 提出、使用者採用〕

| 欄位 | 內容 |
|---|---|
| 假設 | 幣別寫成 `NTD` 的 200 張訂單是台幣，匯率 1 |
| 為什麼需要假設 | 官方沒列幣別值域；`NTD` 不是 ISO 代碼，也不在匯率表 |
| 使用者原話 | AI 列出金額四個子題的建議（含 NTD 當 TWD），使用者接受，理由：「原幣別保留可追溯，換算 TWD 讓營收能直接加總」（process-log「金額：原幣別與換算 TWD 都存」）。這句理由說的是“兩種金額都存”，不是針對 NTD |
| 依據與資料證據 | **支持**：以 1:1 換算時，NTD 的金額比值分布和 TWD 幾乎相同（p50 1.0347 對 1.0506），而且都是整數金額（`order-amount.md` 的 V4；A-3 3.5 節） |
| 用在哪裡 | Part A：`TWD_PEGGED_CURRENCIES` 固定匯率 1，原幣別欄保留 `NTD`。Part C：依幣別分組時要注意原始值有 NTD |
| 如果假設錯了 | 200 張、約 5,456 萬台幣的金額換算錯 |

### 3.3 換匯用台北下單日當天的匯率

〔AI 提出、使用者採用〕；找不到匯率的處理為〔使用者假設〕

| 欄位 | 內容 |
|---|---|

| 為什麼需要假設 | 官方只說 products.csv 是“行程產品主檔”，沒說會不會刪除舊商品 |
| 使用者原話 | 「我認為訂單是主要的事實表 也是分析資料的中心思考分方式 而商品可能經過時間迭代 有消失的可能 因此以進客能保留訂單的方式處理」（process-log「A-3 剩下四題：N2、L3、V6、L11」） |
| 依據與資料證據 | base 有 120 張訂單的產品不在清單；另有 4,747 張的產品 `is_active = 'N'`（A-3 3.5 節） |
| 用在哪裡 | Part A：對不到的訂單照常寫入，`product_sk` = -1（未知產品），保留原本的產品編號；未知商品建佔位列是之後的改善方案。Part C：依產品類型、目的地分組時，會有一組「未知產品」 |
| 如果假設錯了 | 若這 120 個編號是上游錯誤，它們的營收被歸到未知，依產品分組的數字少算 |
