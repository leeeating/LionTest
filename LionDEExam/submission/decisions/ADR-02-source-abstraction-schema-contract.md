# ADR-02｜管線以抽象來源設計，品質規則寫成 schema 合約
- 狀態：草稿
- Part：A
- 關聯：管線以抽象來源設計，品質規則寫成 schema 合約

## 背景
題目給的輸入是 CSV。A-2：「實作管線：先載入 orders_base，再依序處理三個每日增量檔。」官方 `candidate_package/README.md`：「資料為合成資料，模擬真實上游系統的輸出」。現實中這些資料的源頭是營運系統的 SQL DB，CSV 是它每日匯出的結果。

使用者在對齊時提出兩個需求：
- 管線要可遷移：日後源頭換成 SQL DB（或 Fabric 的其他接入方式）時，不必重寫。
- 想用 SQL DB 那種 schema 約束（型別、NOT NULL、CHECK）處理一部分資料品質問題。

CSV 沒有型別與約束，這正是品質問題藏得住的原因。已知的問題中（數字出自 `part_b/evidence.md` E9 與 `notes/dataset/dictionary.md`，A-3 會重跑），schema 約束擋得住和擋不住的各有一些：

| 問題 | 筆數 | schema 約束能否處理 |
|---|---|---|
| base 的負數金額 | 50 | 能擋：`CHECK (amount > 0)` |
| base 的 product_id 不在產品主檔 | 120 | 型別與 CHECK 都擋不住；參照完整性要靠管線檢查（Delta 不支援 foreign key，實作時確認） |
| 疑似多乘 1,000 的金額 | 40 | 擋不住：金額仍大於 0 |
| 幣別寫成 `NTD` | 200 | 用 `CHECK (currency IN (...))` 只能擋，不能把 NTD 對應成 TWD；對應要靠清理規則 |
| 日期格式混用（`YYYY/MM/DD`、`Z`） | 各 3,001 | 型別轉換時才會出錯或被悄悄轉錯；要在轉型前先偵測 |
| city 用字串 `N/A` 表示缺值 | 71 | 擋不住：`N/A` 是合法字串 |

## 選項
| 選項 | 好處 | 代價 |
|---|---|---|
| A. 讀取來源抽成介面＋Delta 表上的 schema 約束，不架 DB | 換源頭只換讀取那一層；約束直接掛在 Delta 表上，和 Fabric Lakehouse 同一套機制；閱卷者不用多起服務 | 「從 SQL 讀」只有介面與說明，沒有實際跑過；約束只能擋不能修，修正仍要靠清理規則 |
| B. 真的架 SQL DB（docker-compose 起 Postgres，CSV 先灌進去，管線用 JDBC 讀） | 源頭最接近現實；DB 的 schema 約束（含 foreign key）真的生效 | 灌資料時違規列會直接失敗，錯誤發生在管線外面，A-3 要的筆數與偵測查詢變難做；多一個服務與一段載入程式，閱卷者 30 分鐘重現的風險變高 |
| C. 直接讀 CSV，不抽介面、不加約束 | 程式最少 | 換源頭要改讀取以後的程式；品質規則散在清理程式裡，沒有一份可對照的合約 |

## 決定〔使用者撰寫〕
〔待使用者確認〕選 A。

## 理由〔使用者撰寫〕
〔待使用者確認〕使用者在對話中的原話：「這個pipline應該要可遷移」、「我也想從sql db schema解決一些資料品質的問題」、「也不用真的架db 這提應該要讓我以抽象設計的方式解決」。

## 後果
- **讀取層**：定義一個來源介面，各實作都回傳同一個明確定義的 schema（欄位名與型別寫成程式中的常數，不靠推斷）。現在只實作 CSV 版；SQL 版在 README 說明介面怎麼接，不實作。
- **約束與隔離的順序**：先在管線裡把違規列分到隔離表並計數，再寫入有約束的表。約束是最後一道防線，若觸發代表前面的檢查漏了。（Delta 的 CHECK 違反時是否讓整批寫入失敗，實作時實測。）
- **schema 管不到的問題仍要清理規則**：多乘 1,000、NTD 對應、日期格式、`N/A`、參照完整性，都在 silver 層的清理與檢查處理，並列進 A-3。
- **A-3 報告**：每個品質問題標明是由 schema 約束、管線檢查、還是清理規則處理。
- **Part C 接得上**：來源介面對應 Part C 裡營運 DB 到 Fabric 的接入方式。
