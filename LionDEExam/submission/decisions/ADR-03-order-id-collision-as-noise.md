# ADR-03｜增量檔與 base 撞號的列當 noise 處理
- 狀態：草稿
- Part：A
- 關聯：增量檔與 base 撞號的列當 noise 處理（[process-log](../ai-collab/process-log.md)）；[order-identity.md 的 J2](../notes/part_a/schema-inference/order-identity.md#j2)、[J4](../notes/part_a/schema-inference/order-identity.md#j4)

## 背景
官方 `candidate_package/README.md`：增量檔「含新訂單與舊訂單的狀態更新事件」，「增量檔中同一 `order_id` 可能出現多次（狀態更新事件），以 `updated_at` 區分新舊」。照這個說法，增量檔裡已在 base 出現過的 `order_id`，應該是那張舊訂單的狀態更新。

資料顯示這些列不像同一張單的更新：
- 每個增量檔約 600 列的 `order_id` 已在 base（day1 603 列、day2 602 列、day3 603 列）。
- 這些列和 base 同 id 那列比較，會員、金額、下單時間**相同的列數都是 0**。
- 幣別、通路、狀態相同的列數，落在「兩疊不相干的訂單隨機配對」的期望值附近，沒有任何一欄高於隨機（下表）。如果是同一張單，這些欄位應該幾乎全部相同：資料裡確定是同一張單的三類重複組，通路、幣別都沒有變（見下方對照組）。

| 欄位 | day1 實際／期望 | day2 實際／期望 | day3 實際／期望 |
|---|---|---|---|
| 會員 | 0／0.1 | 0／0.1 | 0／0.1 |
| 金額 | 0／0.0 | 0／0.0 | 0／0.0 |
| 下單時間 | 0／0.0 | 0／0.0 | 0／0.0 |
| 幣別 | 312／308.2 | 309／310.2 | 299／291.3 |
| 通路 | 157／150.9 | 160／151.0 | 131／150.9 |
| 狀態 | 118／115.7 | 129／124.9 | 108／119.0 |

指令（repo 根目錄）：`python3 -I LionDEExam/submission/part_a/profiling/collision_expected_match.py LionDEExam/candidate_package/dataset`。期望值＝兩邊各自的值分布不變、隨機配對時碰巧相同的列數。

- 對照組：資料裡確定是同一張單的重複列（增量同檔 45 組、day1→day2 的 25 組、base 的 40 組），會員、金額、下單時間全部相同（`notes/part_a/schema-inference/order-identity.md` 的 J1、J4）。
- 撞號列的狀態只有 cancelled 和 completed。若當成 base 那張單的更新，會出現 completed → cancelled，與狀態機「completed 之後不能取消」的假設衝突（`notes/part_a/order-state-machine.md`）。
- 此論證的限制：能證明兩列「統計上無關」，但排除不了「上游允許整張單被改寫」這種業務規則（order-identity.md 的 Q5）。

## 選項
| 選項 | 好處 | 代價 |
|---|---|---|
| A. 當 noise（撞號）：不寫入 fact，進隔離表並計數 | 不會用另一張單的內容覆寫 base 的訂單；會員、金額、營收不被汙染 | 與官方 README 的說法不同；若它們其實是合法更新，這些訂單的狀態變化會缺漏（每天約 600 列） |
| B. 當合法更新：整列覆寫 base 那張單 | 符合官方 README 的文字 | 約 1,800 張 base 訂單的會員、金額、下單時間被換掉，營收與會員歸屬全變；會出現 completed → cancelled 這種違反狀態機的轉移 |
| C. 只採用狀態欄位，其他欄位保留 base 的值 | 折衷，保留狀態更新 | 等於假設「狀態是對的、其他欄位是錯的」，沒有證據支持；狀態本身也跟 base 呈隨機關係 |

## 決定〔使用者撰寫〕
〔待使用者確認〕選 A。使用者原話：「把撞號當 noise 處理」。

## 理由〔使用者撰寫〕
〔待使用者確認〕使用者原話：「先假設訂單狀態不能被改寫」。確認原意：訂單內容（會員、下單時間、金額）不能被改寫，狀態可以變。

## 後果
- **判定規則**：增量列的 `order_id` 已存在，但會員、下單時間、金額任一與既有訂單不同 → 判為撞號，進隔離表。這需要先定義「不可變欄位」（J4）：使用者確認理由「先假設訂單狀態不能被改寫」的原意是訂單內容（會員、下單時間、金額）不能被改寫，狀態可以變。
- **隔離與對帳**：每批輸出「輸入 = 寫入 + 隔離」，撞號列的筆數要能對上（每天約 600 列）。
- **A-3 報告**：說明這與官方 README 不同、證據是什麼、限制是什麼，以及建議上游確認 order_id 的產生方式。
- **增量同檔內的 6 組撞號（J3）**：適用同一條規則。
- **若業務規則證實允許整張單改寫**：要改用選項 B 或 C，隔離表保留了原始列，可以重新處理。
