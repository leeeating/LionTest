# T5 驗收發現的問題

T5（fact_order 的 base 載入、隔離表、對帳）由實作 agent 寫，再交給**沒看過實作過程的驗收 agent** 獨立檢查。共做了 1 輪完整驗收，修正後再做 1 次針對性驗收。另外，撰寫 `model.md` 的文件 agent 在對照程式時，也發現了 README 不一致的地方。本檔列出所有發現，供使用者 review。

- 發現者：沒有另外註明的，都是驗收 agent。
- 怎麼確認修好：實作 agent 修完後，故意把實作改壞，確認新測試會失敗，再還原。

## 總覽
| 輪 | 結論 | 最嚴重的問題 | 後續 |
|---|---|---|---|
| 1 | 有條件過（沒有正確性 bug） | base 截止日的說明和資料不符；增量的舊事件會把狀態蓋回去（屬於 T6） | 修 5 項；狀態倒退列為 T6 必做 |
| 針對性 | **通過** | 無（1 項低嚴重度留給 T6） | 152 個測試在本機與 TZ=UTC 都通過 |

## 第 1 輪先確認正確的部分
- 驗收 agent 只用 csv 和 Decimal，獨立重算 base 的數字，結果和實作完全一致：
  - 輸入 100,040 列，fact 100,000 列，隔離 40 列（全部是 V7 重複，其中 8 組只差下單時間的字串格式）
  - 各幣別筆數：TWD 66,661／USD 22,118／JPY 11,021／NTD 200
  - amount_twd 總和 35,957,084,078.22
  - product 落到 -1 的有 120 列，member 落到 -1 的有 0 列
- member_sk 抽查：會員 M003364 在 05-31 從金卡升為白金；他 05-13、05-19 的訂單對到金卡，06-16、06-30 的訂單對到白金。
- 隔離表保留原始字串，例如 amount 是 `152295.0`，不是 `152295.00`。
- 10 個合成邊界案例都照規則處理，例如：匯率同日重複時整批停、只差金額格式算重複不算撞號、幣別寫成小寫 `ntd` 進隔離表。
- 把實作改壞 9 種寫法，測試都抓得到，例如：匯率改用 inner join、拿掉 NTD 匯率 1、去重保留最舊的一列、隔離表改用 append 寫入、下單日改用 UTC。

## 針對性驗收（第 1 輪修正後）
結論：**通過**。驗收 agent 實測確認：
- 品質規則收到的 as_of 正確。
- product_id 重複時丟出 `ReferenceDataError`，而且 5 張表連同倉儲目錄都沒有建立。
- 截止日的敘述與數字和資料一致。

另外把實作改壞 5 種寫法，新測試都會失敗。

留給 T6 第二階段的低嚴重度問題：「整批停時沒有寫入任何表」這條測試，只檢查了 fact、隔離表、dim_product，沒有檢查 dim_member、dim_date，也沒有斷言 `__cause__`。以後若調整寫入順序，造成部分表先寫入，這條測試抓不到。

## 實作者自己加或自己決定、待使用者確認的
- 匯率表有壞列，或同一天同一幣別重複時，比照產品清單整批停（原規則只要求產品清單）
- dim_member 的違規列只計數，不進訂單隔離表
- amount_twd 以 HALF_UP 四捨五入到小數 2 位
- 找不到當天匯率時進隔離表，不用前一天的匯率（base 實際 0 筆）

## 值得 review 的模式
1. **沒有正確性 bug，但說明和資料不符**：註解寫「07-01 以後屬於增量」，資料卻更新到 07-03。說明寫錯，讀者就會做錯判斷。這類問題只能拿真實資料去查，才查得到。
2. **驗收抓到的問題引出了新的設計決策**：「狀態會被蓋回去」和「去重會吃掉中間事件」，最後演變成狀態機的一連串定案：C、可達性、同一秒狀態不同、斷鏈之後。驗收不只找 bug，也找出規格的缺口。
3. **文件 agent 也能抓到不一致**：寫 model.md 時逐一 grep 欄名與片段，發現 README 和程式有 4 處不一致。
