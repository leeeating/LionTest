# T4 驗收發現的問題

T4（dim_member，SCD Type 2）由實作 agent 撰寫，再交給**沒看過實作過程的驗收 agent** 獨立檢查。共做了 1 輪完整驗收，修正後再做 1 次針對性驗收。本檔列出每一輪抓到的問題，供使用者 review。

- 除非另外註明，問題都是驗收 agent 發現的。
- 「怎麼確認修好」：實作 agent 修完後，故意把實作改壞，確認新測試會失敗，再還原。

## 總覽
| 輪 | 結論 | 最嚴重的問題 | 後續 |
|---|---|---|---|
| 1 | 有條件過 | 回傳的表只含這批受影響的會員，T5 用它對版本會讓其他會員悄悄落到 -1 | 修 4 項，補兩份 README |
| 針對性 | **通過** | 無（1 項低嚴重度留給 T5） | 132 個測試在本機與 TZ=UTC 都通過 |

## 第 1 輪先確認正確的部分
- 驗收 agent 用純 Python（只用 csv 模組）照規則另外計算一次：8,000 位會員、8,772 個版本、772 位有 2 個版本，和實作**0 筆不一致**。
- 一次處理三批，和逐批 MERGE 04-30 → 05-31 → 06-30 的結果相同。
- 11 萬多筆訂單對完版本後，列數不變，落到 -1 的有 0 筆。
- 用合成資料測邊界，全部符合規則：同批三列取最高等級、等級先升再降、city 真實值 → N/A → 另一個真實值、下單日剛好落在版本交界、重送舊快照。

## 第 1 輪

| 嚴重度 | 問題 | 會造成什麼 | 修法 |
|---|---|---|---|
| 中 | `write_dim_member` 的回傳只含這批受影響的會員和 -1 列（處理 06-30 後只有 912 列，全表是 8,773 列） | T5 拿它去 `resolve_member_sk`，沒出現在這批的會員會全部悄悄落到 -1；fact 列數不變，所以對帳也抓不到 | `write_dim_member` 寫入後讀回 Delta 全表再回傳；`build_dim_member` 的回傳欄位改名為 `changes`，避免被誤當全表；`resolve_member_sk` 的 docstring 寫明 dim_df 必須是全表 |
| 中低 | 「不能看到之後的快照」完全靠呼叫端自己過濾 | 呼叫端直接傳整份 members.csv，就會一次吃進三批 | 加必填參數 `through`，函式內只處理 `extract_date <= through` 的列 |
| 低 | 測試沒有涵蓋超過 2 個版本的情況（真實資料最多 2 版） | 版本區間的計算如果改壞，只有在 3 個以上版本時才會出錯，測試抓不到 | 補合成測試，期望值寫死：一般 → 金卡 → 一般得到 3 個版本；台北市 → N/A → 高雄市得到 2 個版本 |
| 低 | 有一條測試的訂單是用 dim 自己的 valid_from、valid_to 產生的 | 它只能證明列數不變，證明不了每張單對到正確的版本 | 註明這條只驗列數；版本是否正確由另一條期望值寫死的測試負責 |

## 針對性驗收（第 1 輪修正後）
結論是**通過**。驗收 agent 用真實資料實測：
- 逐批寫入時，每一步回傳的表都等於 Delta 全表（8,001 → 8,364 → 8,773 列）。
- 用回傳值 resolve 全部訂單，落到 -1 的為 0。
- 傳入三批、`through` 設 05-31，結果和只傳到 05-31 相同。

另外把實作改壞 7 種寫法，每一種都至少有一條測試失敗。

低嚴重度、留給 T5 順手修的一項：`_not_after` 用 `try_cast` 判斷 extract_date，比合約寬鬆，`"2026-07-15 junk"` 這類壞值會被算成「截止日之後」而延後被發現。T5 已改用嚴格的日期格式判斷。

## 實作者自行決定、交給使用者確認的
| 項目 | 實作者的做法 | 使用者的決定 |
|---|---|---|
| city 從 NULL 變成真實值 | 開新版本，不回填舊版本 | 同意：「不是使用null就好」 |
| 第二版以後的 valid_from | 用觀察到變動那一批的 extract_date | 同意：「只記錄確定知道的事」，並指出根本解法在上游（會員表記錄變動時間） |
| `last_seen_extract_date` 擋重送的舊快照 | 以會員為單位判斷 | 副作用（遲到的舊批次會遺失中間歷史）由使用者要求記錄，T6 用批次紀錄強制依序處理 |

## 值得 review 的模式
1. **介面陷阱比計算錯誤更難發現**：資料內容 0 筆不一致，但回傳形狀會讓下一張卡用錯。只看本卡的測試抓不到，要由驗收 agent 站在下一張卡的角度檢查。
2. **「不偷看未來」要由介面強制**：T3 的 `all_orders(days)`、T4 的 `through`，都從「呼叫端自己記得」改成必填參數。
3. **真實資料沒有的情況要用合成資料補**：真實資料最多 2 個版本、沒有新會員，這兩類都只能靠合成測試覆蓋。
