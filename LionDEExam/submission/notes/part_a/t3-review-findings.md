# T3 驗收發現的問題

T3（共用骨架、dim_product、dim_date）由實作 agent 寫，再由**沒看過實作過程的驗收 agent** 獨立檢查，共 5 輪加 1 次針對性驗收。每一輪的問題都退回給實作 agent 修，修完再派新的驗收 agent。本檔列出每一輪抓到的問題，供使用者 review。

- 發現者：除非另外註明，都是驗收 agent。
- 「怎麼確認修好」：實作 agent 修完以後，故意把實作改壞，確認新加的測試真的會失敗，再還原。

## 總覽
| 輪 | 結論 | 最嚴重的問題 | 後續 |
|---|---|---|---|
| 1 | 有條件過 | product_sk 的說明會讓 T5 產生懸空外鍵 | 修 4 項 |
| 2 | 有條件過 | dim_date 處理 base 時偷看到 day3 的日期 | 修 4 項；引出「型別違規」定案 |
| 3 | 有條件過 | 空字串被悄悄讀成 NULL | 讀取層改成全字串＋`cast_to_contract` |
| 4 | 有條件過 | **（高）`count()` 漏算欄位數錯誤的壞列，對帳失真** | 修 4 項 |
| 5 | 有條件過 | 產品清單若有 id 叫 `UNKNOWN`，訂單列數翻倍 | 修 4 項 |
| 針對性 | **通過** | 無 | 109 個測試在本機與 TZ=UTC 都通過 |

---

## 第 1 輪

| 嚴重度 | 問題 | 會造成什麼 | 修法 |
|---|---|---|---|
| 中 | `product_sk()` 的 docstring 寫「T5 可以直接在 fact 端算 sk，不必 join 回維度」 | 訂單裡有 120 個 product_id 不在產品清單，直接 hash 算出的 sk 在 dim_product 找不到；`xxhash64(NULL)` 是 42，不是 NULL | 新增 `resolve_product_sk()`：用 join 對應，對不到的落到 -1 |
| 中 | dim_date 的測試期望值和實作用同一個函式算 | 時區換算算錯了，測試照樣通過（同義反覆） | 改成期望值寫死，例如 `2026-06-25T18:02:16Z` 的下單日應是 06-26 |
| 中低 | 沒有測 Type 1「覆寫」 | 拿掉 MERGE 的 `whenMatchedUpdateAll()`，測試仍然通過 | 補「產品名稱改了以後，表裡的值真的被覆寫」的測試 |
| 低 | 「sk 重跑穩定」的測試抓不到 row_number | sk 改成 row_number，同一份輸入也常產生同樣的編號 | 改成打亂輸入順序、只取一半重建，並寫死一個 sk 值 |

## 第 2 輪

| 嚴重度 | 問題 | 會造成什麼 | 修法 |
|---|---|---|---|
| 中 | 文件說「型別轉不過就報錯」，實際上 Decimal 小數位數超過時會被四捨五入，不報錯 | `100.456` 悄悄變成 `100.46` | 先改文件；這個問題引出「型別違規」的定案（見第 3 輪） |
| 中 | dim_date 範圍「05-01～10-30」沒有測試鎖住 | 範圍算錯也不會被發現 | 補寫死範圍的斷言 |
| 中 | `build_dim_date` 每次都讀 base＋三天增量 | T6 逐日處理時，處理 base 那一刻就看到 day3 的日期，等於偷看未來 | 改成由呼叫端傳入訂單；補「先只用 base 建表，再補 day1」的測試 |
| 低 | dim_date 的冪等測試只比筆數 | 內容改變但筆數相同時抓不到 | 改成比對整表內容 |
| 低（設計提醒） | FAILFAST 和 ADR-02「先隔離並計數」衝突 | 一列型別不合，整批讀取就失敗，到不了隔離 | 交給使用者決定 → 定案「檔案層級整批停、列層級進隔離表」 |

## 第 3 輪

| 嚴重度 | 問題 | 會造成什麼 | 修法 |
|---|---|---|---|
| 中 | 除了 Decimal 四捨五入，空字串也會被悄悄讀成 NULL；`1e2` 會被讀成 `100.00` | 分不出「沒填」和「填錯」 | 依使用者定案，讀取層改成全部讀成字串，再由 `cast_to_contract()` 照合約逐列檢查 |
| 低 | 重跑 MERGE 時，Delta history 會顯示「更新 N 列」 | 用 operationMetrics 證明冪等會誤判 | 文件註明「重寫但值相同」；工作檔記下 T6 冪等證明要比內容 |
| 低 | 產品清單有重複 product_id 時，`dropDuplicates` 任選一列 | 每次重跑可能留下不同的那一列，冪等被破壞 | 改成直接報錯（`DuplicateKeyError`） |
| 低 | 沒有共用的 `date_sk()` | T5 可能另寫一份算法，兩邊不一致 | 抽出公開函式 `date_sk(col)` |
| 低 | README 範例的輸出路徑會寫進 repo | repo 多出沒被 .gitignore 排除的 `out/` | 範例改寫到 `/tmp/...` |

## 第 4 輪

| 嚴重度 | 問題 | 會造成什麼 | 修法 |
|---|---|---|---|
| **高** | 欄位數不符的壞列（少一欄、多一欄、引號不成對等），用 `count()` 數會被算成合格 | T5 對帳「輸入＝寫入＋隔離」會報出隔離 0 筆而且帳是平的，實際上有列該被隔離。原因：Spark 讀 CSV 時的 column pruning 讓 `count()` 不解析欄位 | `build_spark()` 關掉 `spark.sql.csv.parser.columnPruning.enabled`；守恆測試改成 `count()` 和 `collect()` 兩種都斷言 |
| 中 | 必填欄位只填空白（例如 product_id 是 `" "`）會通過 | 無法歸屬的 key 進到 fact | 必填欄位 trim 後是空的也算「必填空值」 |
| 中 | 下單時間是必填，但格式解析失敗時只會悄悄變成 NULL | dim_date 略過這一列，fact 拿到 NULL 的 date_sk，也不進隔離 | 驗證時加「時間可解析」規則；格式定義抽到 `timeparse.py`，驗證和解析共用一份 |
| 中 | 產品清單某一列壞了，該產品的訂單全部落到「未知產品」 | 營收被算進未知，沒有任何警示 | 交給使用者決定 → 定案「產品清單有壞列就整批停」 |
| 低 | `all_orders` 的 days 有預設值（三天全部） | T6 漏傳時會偷看未來 | 拿掉預設值，強制呼叫端傳入 |

## 第 5 輪

| 嚴重度 | 問題 | 會造成什麼 | 修法 |
|---|---|---|---|
| 中 | 產品清單若有一個產品的 id 剛好是 `UNKNOWN`，會和「未知產品」列撞號 | 下次 MERGE 失敗；`resolve_product_sk` 讓訂單列數翻倍 | 產品清單出現保留字就報錯 |
| 中低 | 格式檢查的 regex 結尾用 `$`；Java 的 `$` 也會吻合結尾換行前的位置 | `"3\n"` 這種值會被放行。CSV 碰不到，換成 SQL 來源就會碰到 | `$` 全部改成 `\z`；補 `"3\n"`、`"3\r\n"` 等測試 |
| 低 | README 範例的註解說「建構 `CsvSource` 時就會檢查檔案」 | 實際上要到呼叫讀取方法時才檢查 | 修正註解 |
| 低 | 只查 `_source_error` 一欄會報錯 | T5 統計格式錯誤列時會踩到 | README 加提醒：要從 `cast_to_contract` 的 rejected 計算 |

## 針對性驗收（第 5 輪修正後）
結論：**通過**。109 個測試在本機與 TZ=UTC 都通過；4 項修正逐項實測。驗收 agent 也把實作複製一份改壞，確認新測試會失敗。

---

## 值得 review 的模式
1. **同義反覆的測試出現了兩次**（第 1 輪 dim_date、第 2 輪範圍沒鎖）：期望值和實作用同一個函式算，算錯也會通過。之後的卡在派工時就要求「期望值寫死或用獨立方法算」。
2. **Spark 會悄悄改資料**：四捨五入、科學記號、空字串變 NULL、`count()` 跳過解析、regex `$` 吻合換行。這幾項都不會報錯，只能靠刻意造壞資料去測。這是讀取層改成全字串的原因。
3. **三項問題變成使用者的決策**：型別違規怎麼處理、產品清單壞列怎麼處理、無時區標記的時間怎麼解讀。驗收抓到的不只是 bug，也有規格沒定的地方。
4. **每輪都還有新問題**：5 輪中每輪都是「有條件過」，嚴重度大致逐輪下降，但第 4 輪仍抓到一個高嚴重度問題。
