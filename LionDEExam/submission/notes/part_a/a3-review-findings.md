# A-3 資料品質報告獨立驗收（/tmp/a3_review.md）

結論：**有條件過**。29 項的影響筆數我用獨立 DuckDB 查詢重算，幾乎全部吻合（唯一差異 L11 185 vs 186）。主要缺口是 L10 少了一組反向證據、L3 的分類與遺漏細節，以及可讀性。
臨時腳本：/tmp/a3/s1.py～s21.py（`uv run python -I /tmp/a3/sNN.py`）。

## 1. 報告漏掉的問題（依嚴重度）

### M1（中高）L10 缺反向證據：paid／created 的出發日已過卻沒有 completed
位置：「二、訂單的時間 > L10｜completed 但出發日還沒到」，片段「base 的 completed **全部**在出發日之前」。
查詢（base 每 id 取 updated_at 最新一列）：
```sql
select order_status, count(*), sum(case when dep < date '2026-07-01' then 1 else 0 end) dep_passed_by_0701
from b1 group by 1;
select order_status, sum(case when dep <= upd_local::date then 1 else 0 end) from b1 group by 1;
```
輸出：paid 42,881／9,234、created 14,282／3,053、cancelled 14,241／3,056、completed 28,596／6,149；四種狀態的「出發日 <= 最後更新日」都是 0。
意義：base 裡**每一種狀態**的 updated_at 都早於出發日，而且出發日已過的比例四種狀態都約 21.5%。狀態和出發日看起來互相獨立。在「completed＝出團完成」的假設下，9,234 張 paid 與 3,053 張 created 早該出團卻沒完成，是 L10 的鏡像問題，報告只列了單邊。這是 L10 選項 C（completed＝交易完成）最強的資料證據，應該放進 L10 給使用者決策時參考。

### M2（中）L3 晚到新單：5 張出發日已過才付款
位置：「二、訂單的時間 > L3｜day2 有晚到的新單」。
```sql
select d, order_id, order_status, created_local, upd_local, dep from x
where upd_local::date > dep and order_status='paid';
```
輸出：5 列，都是 day2 的 ORD00112030/039/043/047/053，出發日 06-28～06-30，paid 的時間是 07-02。另外這 60 張的第一個（也是唯一一個）事件都是 paid，沒有 created。報告沒有提。

### M3（低）V5 的 Z 格式跨日筆數沒有量化
位置：「V5｜base 下單時間有三種格式」，片段「`Z` 格式會讓台北 08:00 前下的單落到前一天」。
```sql
select count(*) from x where fmt='Z' and substr(order_created_at,1,10) <> strftime(created_local,'%Y-%m-%d');
```
輸出：1,003 列（3,001 列 Z 格式中的 1,003 列）。建議補上這個數字，「不處理會錯幾筆」才具體。

### M4（低，屬於資訊）會員等級變動模式與 V8 規則
位置：「L9｜等級、城市在快照間改變」、「V8」。
V8 取較高等級時，跨快照的等級變動有 404 次 +1 升級、1 次降級；取較低等級時是 405 次全部 +1 升級，沒有降級。V8 的 30 人裡只有 2 人出現在後續快照，後來的等級一人等於較低值、一人等於較高值，證據各半，推翻不了使用者的決定。不過「真實的等級變動全部是升一級」這件事，報告沒有寫。

### M5（低）L6 的增量筆數混入了撞號列
位置：「L6｜訂單的產品已下架」，片段「base 4,270、day1 184、day2 182、day3 195」。
真正的新單只有 164／154／163，其餘是 J2 的撞號列，不會進 fact。建議加註。

## 2. 數字不一致
- **L11 185 vs 186**（「L11｜後續快照與前一次完全相同」，片段「185 列（05-31 94、06-30 91）」）。`Q-L11.identical` 用 `ORDER BY extract_date, member_level` 打平同日兩列，member_level 是中文字串排序，不是業務等級順序。照 V8 的決定先取較高等級再比，05-31 是 95，合計 186。差 1 列，原因就是這個排序。
- **L1 的措辭**（片段「day2 有 6 列早於批次日（就是 L4 那批較舊的事件）」）：這 6 列確實都屬於 L4，但 L4 有 25 列（07-01 有 6、07-02 有 7、07-03 有 8、07-04 有 4）。現在的寫法讀起來像 L4＝6 列。建議改成「這 6 列是 L4 25 列中的一部分」。
- 其餘全部吻合：V7 40/40/8、J2 603/602/603（較舊的 12）、J3 6 組 12 列、N1 每檔 15（其中 id 在 base 的 3/2/3）、L4 25、V5 3,001+3,001、Z 早於 05-01 的 13 列、L1 3,290/3,257/3,263、L2 2,265、L3 60、L10 28,612/28,596、10,320,108,224、V1 50（29/17/4）、-12,389,441.87、V2 40（27/9/4）、10,102,491,689.70、28.10%、V3 300、V4 200、V6 120、L5 80、L6、L7 44 名稱、L12 66,890、比值範圍 0.8378～1.2839、V8 30、V9 71/70、V10 81/80、J9 14+5、L8 455/398、L9 434/376。

## 3. 分類疑慮
「可能合法」7 項逐項判斷：
- L1 增量 updated_at 晚於批次日：可接受。但這屬於 A-2 要求說明的「增量狀況」，可以在 A-2 文件引用。
- L2 base 有 07 月的 updated_at：可接受。
- **L3 晚到新單：不建議放在「可能合法」**。這是典型的晚到資料情境，應該是題目刻意埋的增量狀況之一，A-2 也明確要求說明策略。「當新單寫入、不依批次日分區覆寫」是一個處理決策，應該改成「已決定」並請使用者補一句理由，同時補上 M2 的 5 張出發後付款。
- L5 JPY 帶小數：可接受。也可以考慮依 ISO 4217（JPY 小數位 0）列為格式違規，嚴重度低。
- L6 產品已下架：可接受，因為沒有下架日期，資料無法判斷。需加 M5 的註記。
- L7 同名多 id：可接受。
- L8 未滿 18 歲註冊：可接受。年齡分布從 12 歲起平滑遞增，看起來是產生器的均勻分布，不像刻意埋的錯誤。
防護性設計的 0 筆：fx_missing、值域、會員對不到、往回走的轉移、跳過中間狀態、同時出現在 05-31 與 06-30 的會員、register 晚於 extract，我都獨立重算，確認是 0。增量內（排除撞號）的轉移只有 created→created、paid→paid、paid→cancelled。

## 4. 查詢邏輯
- `Q-L11.identical`、`Q-J9.birth_direction` 用字串 member_level 當打平順序（見第 2 節）。J9 的結果不受影響，L11 差 1。
- `Q-L6.inactive` 沒有排除撞號列（M5）。
- 時區：腳本有 `SET TimeZone='Asia/Taipei'`，TS_NORM 把無標記補成 +08:00、Z 補成 +00:00，正確。比值用下單日（台北）匯率，正確。沒有發現字串比大小的錯誤（`a.src < b.src` 比的是 day1/day2/day3，結果正確）。

## 5. 可讀性（前 3）
1. **內部編號與施工術語沒有定義就出現**：T4／T5／T6、ADR-03、`process-log「…」`、`notes/part_a/...`、「工作檔」「規則卡」「實作者自加」。閱卷者看不懂 T6 是什麼，例如「已決定（J6），**T6 尚未實作**」。建議全部換成功能描述，或在開頭定義一次。
2. **篇幅太長，摘要表之後有大量過程與限制**（937 行）：J2 的對帳拆解（「day1 的 603 = 594 + 6 + 3」）、資料限制 9～11 的長段、附錄的 notes 差異、「審閱提示〔定稿前刪除〕」。建議把對帳細節移到附錄，主文每項維持「描述／筆數／查詢／決策」四段，並記得刪掉審閱提示。
3. **「待使用者決定」「待使用者補理由」「T6 前的管線」這類未完成標記散落全文**（V1、V2、V3、J10、N2、L10、V6、L11、L4 的驗證是「目前錯的」）。繳交版必須全部收斂；L4 的 `[P-L4.after_day3]` 現在寫的是 25 列被蓋回 paid，繳交前一定要重跑。
