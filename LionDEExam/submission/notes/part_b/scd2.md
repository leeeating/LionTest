# SCD2 是什麼、這份程式錯在哪

回到入口：[README.md](README.md)

## 一句話

SCD（**Slowly Changing Dimension**，緩慢變化維度）Type 2：維度資料改了不覆蓋，舊版留著，標上有效期間。

- **Dimension（維度）**：描述事實的表，例如會員、產品。訂單上的「誰買的」「買了什麼」，答案在維度表裡。
- **Slowly Changing（緩慢變化）**：屬性會變，但變得慢，例如會員幾個月才升一次等。
- **Type 1、2 只是編號**：Type 1 直接覆蓋、不留歷史；Type 2 保留舊版本。

## 例子

會員王小明 4/30 的快照是銀卡，5/31 的快照已經是金卡。

- **SCD1（直接覆蓋）**：名冊只剩「金卡」。之後查「5/15 那筆訂單是什麼等級下的」，會答成金卡，答錯了。
- **SCD2**：兩版都留，各自標有效期間：

| member_id | 等級 | valid_from | valid_to | is_current |
|---|---|---|---|---|
| M001 | 銀卡 | 2026-04-30 | 2026-05-31 | false |
| M001 | 金卡 | 2026-05-31 | 9999-12-31 | true |

查 5/15 的訂單，就找「5/15 落在哪一列的區間內」，得到銀卡；5/31 的訂單則落在金卡那一列。區間是半開的：含 `valid_from`、不含 `valid_to`（`valid_from <= order_date < valid_to`），所以舊版的 `valid_to` 和新版的 `valid_from` 同一天也不會讓那天的訂單同時對到兩版。

**Python 類比**：SCD1 是 `member["M001"] = "金卡"`，舊值就沒了；SCD2 是一個 list，每次變更都 append 新版本，並把上一版的 `valid_to` 填上日期。

**每次更新要做三件事**：
1. **關舊版**：目前版本的 `valid_to` 填上日期，`is_current` 改成 false。
2. **加新版**：插入新的一列，`valid_to` 寫 9999-12-31（代表「到現在都有效」）。
3. **沒變就不動**：屬性沒變的會員，不要多產生一個版本。

## 這份程式的問題

`update_dim_member` 自稱 SCD2，但三件事都沒做對：
- 沒有 `valid_to`、`is_current`，舊版沒有被關閉。
- 寫入時用 overwrite 加 `"replaceWhere", "member_id IS NOT NULL"`，等於整張表覆寫，只剩有變更的會員，連 SCD1 都不如。
- 用 `dim.alias("d").join(latest_snap.alias("s"), "member_id")`（inner join）偵測變更，dim 裡還沒有的新會員永遠進不來；`!=` 遇到 null 會漏掉變更。

資料佐證：`members.csv` 有 989 人有多筆快照，其中 434 人等級變過、376 人縣市變過。這些就是 SCD2 該保存的歷史。

## 建議修法

用 Delta MERGE 分兩段：先把有變更的會員的目前版本關閉（設定 `valid_to`、`is_current=false`），再插入新版本和新會員。比較時用 null-safe 的 `eqNullSafe`。完整寫法見報告 4.3。

**陷阱：只拿最新快照，歷史就沒了。** 上面的 MERGE 每次只拿每位會員最新的 `extract_date`，這只適合 dim 已經有歷史之後的每日增量。dim 從空表開始時，如果直接拿現在的 `members.csv` 跑，每人只會建出最新那一版，04-30、05-31 的舊版永遠進不來，上面那 434 人的舊等級就丟了，等於退化成 SCD1。再搭配半開區間 join，早於這唯一一版 `valid_from` 的訂單對不到任何版本，等級變成 null：day1 去重後 4,597 張中有 49 張是這樣。

**Python 類比**：好比上面那個 list，初始化時只 append 了最後一筆，前面的版本從沒放進去。

**初始載入的做法**（二選一，之後再接每日增量）：
- 依 `extract_date` 由舊到新逐批跑同一段 MERGE（04-30 → 05-31 → 06-30）：最單純，屬性沒變的批次自然不會多一版。
- 一次性從全部快照算出每一版的 `valid_from`、`valid_to`：要自己合併「相鄰兩筆屬性相同」的快照，也要先處理同日同分。

**第一版的 `valid_from` 定在哪**（業務定義，要確認）：
- 第一筆快照的 `extract_date`：只記實際看到的；早於它的訂單會對不到（目前資料，不含被隔離的 28 位同分會員：day1 有 17 張對不到，要靠 #6 的隔離告警處理，其餘 0 張）。
- `register_date`：從註冊起就有一版；但註冊時的等級是推定的，不是觀測到的。
- 很早的固定日期（例如 1900-01-01）：一定對得到；同樣是推定，而且看不出哪段是推定的。

細節與數字見報告 #6 (c)「初始載入」。
