## 1. 兩道防線
- **防線一：答案打亂測試**，放在 CI，每次修改特徵管線都自動跑，沒通過就不能合併。專門擋「特徵含有自己的答案」。
- **防線二：影子測試與上線監控**，放在上線前後。最後一道防線，擋「離線和上線對不上」。

## 2. 防線一：答案打亂測試（CI）

**原理**：把 label 隨機打亂，訂單和答案之間的真實關係就被破壞，正常的特徵預測不了，AUC 應該接近 0.5。如果打亂後 AUC 仍明顯高於 0.5，代表有特徵是用這筆訂單自己的 label 算出來的：打亂後的 label 跟著被算進特徵，特徵照樣「猜中」。

```python
def test_label_shuffle(orders, pipeline, seeds=range(5)):
    aucs = []
    for seed in seeds:
        shuffled = orders.copy()
        shuffled["label"] = rng(seed).permutation(shuffled["label"])   # 打亂答案
        aucs.append(pipeline.build_train_evaluate(shuffled))           # 特徵、切分、訓練、評估整條重跑
    assert not significantly_above(aucs, 0.5), f"打亂 label 後 AUC 仍偏高：{aucs}，特徵可能含有答案"
```

- **門檻**：檢定「打亂後 AUC 的平均」是否顯著高於 0.5，不用固定的寬鬆值。
- **成本**：每次 CI 多跑幾次完整流程，資料用固定的抽樣以控制時間。
- **限制**：自己的 label 在特徵裡佔比越小，訊號越弱，越難測出。

## 3. 防線二：影子測試與上線監控

**影子測試**：新模型接上真實訂單，只預測、不採用，業務照舊。

取消的答案要到出發日才揭曉，所以分兩種指標：
- **先行指標（預測當下就有）**：比較線上算出的特徵和離線訓練時的分布、缺值率。例如某個特徵上線時大多是空值（本次的 D1），這裡馬上看得到。
- **結果指標（出發後才有）**：只用「出發日已過」的訂單計算線上 AUC，取消與未取消一視同仁，避免提早出現的取消單讓結果偏掉；再和離線比較。

**放行**：先行指標沒有異常，結果指標也接近離線，才正式採用。

**上線後**：持續看這兩種指標，異常就告警或退回舊模型。業務若會依預測去挽留客人，要保留一組不介入的對照組來算結果指標，否則介入本身會改變取消結果。

## 4. 擋得住哪一類問題
| 問題類型 | 本次的例子 | 防線一 | 防線二 |
|---|---|---|---|
| 特徵含自己的答案 | 2.1、2.2 的取消率 | ✅ | ✅ |
| 偷看未來 | 2.2 用到別筆訂單的未來結果、2.3B 隨機切 | ❌ 打亂後別筆的答案也亂了 | ✅ 特徵分布有差就先行指標發現；否則等結果指標 |
| 訓練與上線算法不一致（和 label 無關的） | 訓練和上線各寫一套程式、時區處理不同 | ❌ | ✅ 先行指標 |

註：D1（上線時會員×產品取消率大多是空值）是 2.1 在上線端的症狀，源頭是同一個特徵含自己的答案，所以防線一會透過 2.1 擋下；防線二的先行指標也看得到。

**使用者接受的代價**：偷看未來的問題，CI 擋不到；分布上看不出差異的（例如只有隨機切），要等結果指標，也就是要等訂單出發。

**考慮過、沒採用的**：改未來資料測試（CI 擋偷看未來）、共用特徵函式（已寫進修正設計原則 4）、單一特徵太準就警報，以及 DE 角度的資料合約與時間點查詢。使用者選擇維持兩道防線。
